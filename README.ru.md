# usedesign

**Одно описание на операцию. Каждый экран, контракт, тест и миграция ссылаются на него.**

*[English version](README.md)*

---

## Проблема

Спроси у зрелой системы: *«что она вообще умеет и в каком состоянии каждая из этих вещей?»* —
и внятного ответа не будет. Не потому, что никто не знает, а потому, что знание разложено по
жанрам, которые между собой не сходятся:

- **спецификация API** знает эндпоинты — но не экраны, не тесты и не смысл;
- **записи решений** знают «почему» — но не знают, что их воплощает;
- **тесты** знают, что проходит — и никогда не знают, что не покрыто;
- всё остальное живёт в комментариях кода и в головах.

Итог предсказуем. Экран расходится с API. Тесты зелёные, а целая ветка поведения не проверена
ни разу. Осознанное архитектурное решение сохраняется только комментарием, который прочтёт
один человек.

## Идея

Описать каждую операцию **один раз** — в файле, который читают и человек, и машина, — и заставить
все артефакты ссылаться на неё.

```
Сценарий   — цель человека, человеческими словами   «Читатель берёт книгу»
  └─ Операция — одно атомарное действие, устойчивый id   library.loan.checkout
       └─ Шаг  — одна стадия внутри действия              s3-member-standing
```

Тесты цепляются к шагам. Экраны объявляют, какие шаги они закрывают. Миграции цепляются к оси
версий. Ничего не остаётся домысливать.

```yaml
steps:
  - id: s3-member-standing
    text: У читателя нет блокирующих ограничений
    on_violation: { error: member_blocked, http: 403 }

tests:
  - { id: CheckoutTests.blocked_member_cannot_borrow, covers: s3-member-standing, level: integration }

interfaces:
  ui:
    screen: CirculationDesk
    covers_steps: [s3-member-standing, s5-commit]
```

Теперь у вопроса *«чем это поведение доказано и где оно показано человеку?»* есть ответ на одном
экране. А отсутствие ответа — **видимая строка**, а не тишина.

## Пять осей

Единственное, на чём формат настаивает жёстко: **этап жизни — это не одно поле.** Пять разных
вещей меняются с пятью разными скоростями, и попытка сложить их в один `stage` — ровно то, отчего
подобные схемы разваливаются через полгода.

| Ось | На какой вопрос отвечает |
|---|---|
| **Зрелость** | Насколько операция построена? |
| **Шаги** | Что происходит при выполнении, включая ветки отказов? |
| **Стадия данных** | Что операция делает с состоянием записи? |
| **Версия** | С какой миграции она ведёт себя именно так? |
| **Асинхронное задание** | Какова жизнь фоновой работы, которую она запускает? |

Тест цепляется к *шагу* и самим своим существованием двигает *зрелость*. Миграция не цепляется
ни к тому, ни к другому — именно поэтому во всех прочих схемах прослеживаемости миграции
остаются сиротами.

## Чем это НЕ является

- **Не новый язык.** YAML-шапка и Markdown. Ни компилятора, ни рантайма, ни привязки к вендору.
- **Не замена OpenAPI.** Спецификация API описывает эндпоинты; карточка описывает операцию,
  которая может охватывать несколько эндпоинтов, экран, фонового воркера и миграцию.
  Спецификация **порождается** из карточек, а не наоборот.
- **Не документация.** Документация необязательна и гниёт молча. Карточки задуманы так, чтобы
  их проверяли автоматически и чтобы расхождение падало громко.

## Статус

**v0.2, черновик.** Формат закалён на восьми операциях реальной боевой системы: карточки писались
по замеру кода, и каждое место, где формат ломался, записывалось. Сломался дважды, в семи местах.
Критерий версии 1.0 — **не** «поломки кончились» (непройденные области всегда что-то сломают), а
*заход, который меняет только опциональные поля и не трогает обязательные*.

Потом спецификацию сверили с её же схемой и примерами — и она разошлась в семи местах уже
другого рода: поле, которое схема принимает, а спека не описывает нигде; правило, объявленное
прозой и никем не проверяемое; один термин, написанный двумя способами в двух файлах. Всё
исправлено до публикации — и записано, потому что это самый честный аргумент в пользу третьей
проверки из списка ниже. Спецификация — такое же описание, как любое другое, и расходится с тем,
что описывает, ровно так же.

| | |
|---|---|
| [SPEC.md](SPEC.md) | Формат: поля, правила и обоснование каждого |
| [schema/](schema/operation-card.schema.json) | JSON Schema для шапки карточки |
| [examples/](examples/) | Пять карточек на выдуманной библиотечной системе |
| [tests/conformance/](tests/conformance/) | Общий корпус, который обязана проходить каждая реализация |
| [design/](design/) | Разборы — вопросы, продуманные до того, как попасть в спецификацию |
| [impl/](impl/) | Реализации, по каталогу на язык |
| [docs/](docs/) | Анимированный рассказ обо всём перечисленном |

## Устройство репозитория

Формат языконезависим — YAML-шапка, Markdown и обычная JSON Schema, — поэтому в корне лежит
только спецификация. Инструменты живут в `impl/`, по каталогу на язык, и своего сборочного файла
корень не имеет.

Всё, что в `impl/`, отвечает перед [`tests/conformance/`](tests/conformance/): это общий набор
карточек с согласованными вердиктами **и согласованными кодами ошибок**. Без него «валидная
карточка» незаметно превращается в «карточку, которую принимает установленный у тебя валидатор» —
та же болезнь, только этажом выше. Корпус написан до первой реализации намеренно: так он описывает
формат, а не закрепляет баги одного инструмента.

Референсной реализацией должен стать TypeScript — выбран по причинам, изложенным в [impl/](impl/),
а не по умолчанию. **Он ещё не написан**: сегодня в репозитории лежит прототип на Python, который
держит корпус честным. Написать иначе значило бы заявить зрелость выше доказательств — ровно то,
чего формат не прощает карточке.

## Дорожная карта

- [x] Спецификация и схема
- [x] Разобранные примеры
- [x] Корпус соответствия — 14 кейсов, вердикты и коды
- [x] Проверка №1 спроектирована и прототипирована — [перечень маршрутов](schema/route-inventory.schema.json),
      нормализация путей, исключения, которые отчитываются, что скрыли
      ([разбор](design/route-conformance.md))
- [x] Проверка №2 спроектирована и прототипирована — названный карточкой тест обязан существовать,
      выполниться, пройти и не быть пропущенным ([разбор](design/step-coverage.md))
- [x] Проверка №3 спроектирована и прототипирована — путь к реализации обязан существовать, а
      единственное непроверяемое утверждение взамен истекает ([разбор](design/maturity-evidence.md))
- [ ] `usedesign validate` — проверка карточек по схеме и межкарточным правилам
- [ ] `usedesign gen openapi` — вывод контракта API из карточек
- [ ] `usedesign check` — три инварианта: нет необъявленных маршрутов, нет недоказанных шагов,
      нет зрелости выше доказательств

Последний пункт — главный. Каталог без проверяющего превращается в благие намерения за считанные
месяцы.
