# usedesign

**Одно описание на операцию. Каждый экран, контракт, тест и миграция ссылаются на него.**

[![conformance](https://github.com/nistoc/usedesign/actions/workflows/conformance.yml/badge.svg)](https://github.com/nistoc/usedesign/actions/workflows/conformance.yml)

*[English version](README.md)* · **Стартовый набор для команды: [starter-kit/](starter-kit/)**

---

## Проблема

Спроси у зрелой системы: *«что она вообще умеет и в каком состоянии каждая из этих вещей?»* —
и внятного ответа не будет. Не потому, что никто не знает, а потому, что знание разложено по
жанрам, которые между собой не сходятся:

- **спецификация API** знает эндпоинты — но не экраны, не тесты и не смысл;
- **записи решений** знают «почему» — но не знают, что их воплощает;
- **тесты** знают, что проходит — и никогда не знают, что не покрыто;
- всё остальное живёт в комментариях кода и в головах.

Итог предсказуем. Экран расходится с API. Тесты зелёные, а целая ветка поведения не проверена
ни разу. Осознанное архитектурное решение сохраняется только комментарием, который прочтёт
один человек.

## Идея

Описать каждую операцию **один раз** — в файле, который читают и человек, и машина, — и заставить
все артефакты ссылаться на неё.

```
Сценарий   — цель человека, человеческими словами   «Читатель берёт книгу»
  └─ Операция — одно атомарное действие, устойчивый id   library.loan.checkout
       └─ Шаг  — одна стадия внутри действия              s3-member-standing
```

Тесты цепляются к шагам. Экраны объявляют, какие шаги они закрывают. Миграции цепляются к оси
версий. Ничего не остаётся домысливать.

```yaml
steps:
  - id: s3-member-standing
    text: У читателя нет блокирующих ограничений
    on_violation: { error: member_blocked, http: 403 }

tests:
  - { id: CheckoutTests.blocked_member_cannot_borrow, covers: s3-member-standing, level: integration }

interfaces:
  ui:
    screen: CirculationDesk
    covers_steps: [s3-member-standing, s5-commit]
```

Теперь у вопроса *«чем это поведение доказано и где оно показано человеку?»* есть ответ на одном
экране. А отсутствие ответа — **видимая строка**, а не тишина.

## Оси

Единственное, на чём формат настаивает жёстко: **этап жизни — это не одно поле.** Шесть разных
вещей меняются с шестью разными скоростями, и попытка сложить их в один `stage` — ровно то, отчего
подобные схемы разваливаются через полгода.

| Ось | На какой вопрос отвечает |
|---|---|
| **Зрелость** | Насколько операция построена? |
| **Шаги** | Что происходит при выполнении, включая ветки отказов? |
| **Стадия данных** | Что операция делает с состоянием записи? |
| **Версия** | С какой миграции она ведёт себя именно так? |
| **Асинхронное задание** | Какова жизнь фоновой работы, которую она запускает? |
| **Продолжение** | Не остановлена ли она в ожидании решения человека? |

Тест цепляется к *шагу* и самим своим существованием двигает *зрелость*. Миграция не цепляется
ни к тому, ни к другому — именно поэтому во всех прочих схемах прослеживаемости миграции
остаются сиротами.

## Чем это НЕ является

- **Не новый язык.** YAML-шапка и Markdown. Ни компилятора, ни рантайма, ни привязки к вендору.
- **Не замена OpenAPI.** Спецификация API описывает эндпоинты; карточка описывает операцию,
  которая может охватывать несколько эндпоинтов, экран, фонового воркера и миграцию.
  Спецификация **порождается** из карточек, а не наоборот.
- **Не документация.** Документация необязательна и гниёт молча. Карточки задуманы так, чтобы
  их проверяли автоматически и чтобы расхождение падало громко.

## Статус

**v0.2, черновик.** Формат закалён на операциях реальной боевой системы: карточки писались по
замеру кода, и каждое место, где формат ломался, записывалось. Сломался трижды, в двенадцати
местах. Критерий версии 1.0 — **не** «поломки кончились» (непройденные области всегда что-то
сломают), а *заход, который меняет только опциональные поля и не трогает обязательные*.

Последний заход сломал формат в пяти местах и дал шестую ось (`continuation`), три новых
необязательных поля, четыре новых проверки — и одну находку ценнее прочих: поле `reversibility`
было обязательным и **не имело честного значения для операции чтения**, поэтому обе read-only
карточки репозитория заявляли `reversible`. Формат, который требует ответа, обязан дать
правдивый, иначе он производит ровно ту ложь, ради борьбы с которой создан. См.
[SPEC §8.1](SPEC.md).

**Затем его направили на систему, которой он никогда не видел** — другой продукт, другая
предметная область. Первый дефект вскрылся *до написания первой карточки*: тот API записывает
действия как `POST /progress/{id}:finish`, нормализация путей читала суффикс как параметр, и
восемь маршрутов схлопывались в две формы. Объяви один — и сверщик считает объявленными все,
после чего отчитывается «чисто». **Сверщик, тихо переставший проверять, выглядит точно как
здоровый репозиторий.**

Дальше ещё три: пакетную операцию с отказами по элементам внутри успешного ответа нельзя было
записать правдиво; несколько операций на одном маршруте считались дефектом, а не обычным приёмом
REST; и правило из прошлого захода оказалось подогнано под свой единственный пример. Две вещи,
прежде лишь обоснованные рассуждением, устояли. Ничего из этого нельзя было найти на исходной
системе: **формат, обкатанный на одном проекте, отчасти описывает этот проект**, и узнать, какая
часть, можно только унеся его в другое место. См. [SPEC §8.0](SPEC.md).

Ранее спецификацию сверили с её же схемой и примерами — и она разошлась в семи местах уже
другого рода: поле, которое схема принимает, а спека не описывает нигде; правило, объявленное
прозой и никем не проверяемое; один термин, написанный двумя способами в двух файлах. Всё
исправлено до публикации — и записано, потому что это самый честный аргумент в пользу третьей
проверки из списка ниже. Спецификация — такое же описание, как любое другое, и расходится с тем,
что описывает, ровно так же.

| | |
|---|---|
| [SPEC.md](SPEC.md) | Формат: поля, правила и обоснование каждого |
| [schema/](schema/operation-card.schema.json) | JSON Schema для шапки карточки |
| [examples/](examples/) | Пять карточек на выдуманной библиотечной системе |
| [tests/conformance/](tests/conformance/) | Общий корпус, который обязана проходить каждая реализация |
| [design/](design/) | Разборы — вопросы, продуманные до того, как попасть в спецификацию |
| [impl/](impl/) | Реализации, по каталогу на язык |
| [docs/](docs/) | Анимированный рассказ обо всём перечисленном |

## Устройство репозитория

Формат языконезависим — YAML-шапка, Markdown и обычная JSON Schema, — поэтому в корне лежит
только спецификация. Инструменты живут в `impl/`, по каталогу на язык, и своего сборочного файла
корень не имеет.

Всё, что в `impl/`, отвечает перед [`tests/conformance/`](tests/conformance/): это общий набор
карточек с согласованными вердиктами **и согласованными кодами ошибок**. Без него «валидная
карточка» незаметно превращается в «карточку, которую принимает установленный у тебя валидатор» —
та же болезнь, только этажом выше. Корпус написан до первой реализации намеренно: так он описывает
формат, а не закрепляет баги одного инструмента.

Эталонная реализация — [TypeScript](impl/typescript/), выбран по причинам, изложенным в
[impl/](impl/), а не по умолчанию. Он проверяет карточки по схеме и межкарточным правилам,
выполняет все три проверки и проходит оба корпуса — **24 / 24 карточек и 23 / 23 по репозиторию**.

```bash
npx usedesign check usedesign.config.yaml
```

Ставить ничего не нужно. Пакет несёт свою копию схемы и не требует, чтобы этот репозиторий
лежал где-то рядом, — именно это делает его пригодным внутри чужого CI.

Прототип на Python остаётся. Корпус, с которым согласна лишь одна реализация, описывает уже не
формат, а эту реализацию, — поэтому CI гоняет обе и сличает, что они говорят об одном и том же
репозитории.

      ([разбор](design/route-conformance.md))
- [x] Проверка №2 спроектирована и прототипирована — названный карточкой тест обязан существовать,
      выполниться, пройти и не быть пропущенным ([разбор](design/step-coverage.md))
- [x] Проверка №3 спроектирована и прототипирована — путь к реализации обязан существовать, а
      единственное непроверяемое утверждение взамен истекает ([разбор](design/maturity-evidence.md))
- [x] `usedesign validate` — карточки по схеме **и** по межкарточным правилам
- [x] Проверка №4 — хранилище: заявления карточек против ключей и индексов, которые живая
      база объявляет о себе сама (SPEC §7.4)
- [x] Проверка №5 — экран против контракта формы: единственная проверка, чей эталон
      **авторский**, а не замеренный — владелец пишет, что экран обязан показывать, тест
      рендерит настоящие компоненты, и ошибки этой проверки — список дел продукта (SPEC §7.5);
      контракты валидируются именованными кодами, группировка по назначению включена, состав
      групп сверяется по цепочкам контейнеров; контракт умеет быть написан раньше экрана,
      описывать семейство элементов по шаблону и отображать состояния экрана на состояния данных
- [x] `usedesign check` — пять проверок, держат корпус из 39 случаев; репозиторий объявляет,
      какие проверки к нему применимы (`checks: [5]`, SPEC §7.6)
- [x] `usedesign scaffold` — заготовка карточки на каждый неописанный маршрут; каждая нарочно
      не проходит валидацию, пока человек её не дозаполнит
- [x] `usedesign preview` — контракты форм страницей из трёх рейлов: дерево, текст и грубый
      каркас с вердиктом на каждом элементе
- [x] [starter-kit/](starter-kit/) — стартовый набор для команды: проверки 1–3 в чужом
      репозитории за час, с честным списком сырого
- [x] Эталонная реализация на TypeScript, оба корпуса в CI на трёх версиях Node плюс работа,
      которая требует, чтобы намеренно гнилой стенд по-прежнему падал
- [x] Опубликован в npm с подписью происхождения — `npx usedesign` работает без клона
- [x] `usedesign gen openapi` — контракт API ИЗ карточек, направление, обратное `scaffold`:
      задуманная операция получает контракт ДО кода. Коды ответов названы исходами и нарушенными
      шагами; замкнутый круг проверяется скармливанием порождённого документа обратно
      `scaffold` — тот обязан отчитаться «неописанных маршрутов ноль»

Проверяющий и есть смысл: каталог без него превращается в благие намерения за считанные месяцы.
Теперь он есть, на двух средах, и CI сличает, что они говорят об одном репозитории, — потому что
два инструмента, согласные, что «что-то сломано», но расходящиеся в том, ЧТО именно, — это уже
начало диалектов.
